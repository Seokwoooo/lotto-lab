# 로또 시뮬레이션 · Lotto Simulation

[무료로 돌려보기](https://lucianlabs.dev/lotto/) · [GitHub](https://github.com/Seokwoooo/lotto-simulation)

로또 100만원치, 1,000게임을 한 번 추첨하면 내 운은 어떨까요?
구매 영수증에서 번호를 먼저 확인하고 추첨하면 내 결과가 얼마나 드문지 확률과 이유를 보여줍니다.
구매 게임 수와 추첨 횟수를 바꿔 장기간 실험할 수도 있습니다.

![로또랩 미리보기](assets/og-image.png)

## 기능

- 직접 추첨하면 약 7초 동안 카운트다운, 공 섞기, 당첨번호 6개와 마지막 보너스 공 공개를 재생한 뒤 결과로 넘어갑니다. 공은 실제로 뽑힌 순서로 공개하며 계산·등수·시드는 바뀌지 않습니다. 여러 회차 실험은 마지막 회차를 보여주고 전체 결과를 합산합니다. 건너뛰기 버튼과 Escape·백그라운드 건너뛰기를 제거해 새 추첨은 번호 공개를 끝까지 기다립니다. 모션 감소에서는 움직임을 없애되 같은 시간을 기다립니다. 계산 중단은 완료한 회차까지만 정리하며 번호 공개는 그대로 마칩니다. 공유 링크는 연출 없이 바로 결과를 엽니다.
- 결과의 다음 추첨 버튼은 100만원 → 1천만원 → 1억원 → **10억원** 순서입니다. 10억원은 자동 1,000게임 × 1,000회, 총 100만 게임이며 20만 장의 영수증을 탐색할 수 있습니다. 설정에서 금액을 바로 선택하거나 10억원을 계속 반복할 수 있습니다.
- 10억원 도전을 시작한 시점부터 완료한 가상 구매 금액과 도전 횟수를 합산합니다. 처음 1등을 만나면 기존 1등 카드에 **“드디어… N번째 10억원 도전에서 / 지금까지 총 N원 써서 1등 당첨!!!”**을 크게 표시합니다. 금액은 당첨이 나온 실험까지 구매한 전체 게임 비용이며, 당첨 게임 직전까지만 계산한 금액이 아닙니다. 중단한 실험은 완료한 게임만 합산합니다.
- 누적 기록은 이 탭의 `sessionStorage`에 요약 한 건만 저장합니다. 새로고침과 같은 결과 재열람은 횟수를 늘리지 않고, 공유 결과는 내 도전으로 합산하지 않습니다. 첫 1등 이후 다음 10억원 도전은 새 누적 기록으로 시작합니다. 설정 화면에서 미완료 도전을 이어갈 수 있고 운 풀이 안에서 기록을 초기화할 수 있습니다. 저장소를 쓸 수 없으면 현재 페이지의 메모리에서만 유지합니다.
- 당첨 누적 금액·횟수는 공유 문구와 저장 이미지에도 표시합니다. 공유 링크는 **마지막 한 번의 실험**을 재현하며, 다른 사람의 누적 기록을 받는 사람의 개인 기록에 넣지 않습니다.
- 결과 화면을 열기 전에 캐릭터 이미지·로고를 디코딩하고 글꼴을 준비합니다. 이미지를 미리 요청하며, 준비가 실패하거나 5초를 넘으면 고정된 대체 화면으로 표시해 늦게 도착한 이미지가 튀어나오지 않게 합니다.
- 기본 1,000게임·1회 추첨. “100만원치 바로 돌려보기”, 가상 구매 1,000,000원, 실제 지출 0원.
- 1,000게임을 5게임씩 200장의 영수증으로 나눠 표시. 추첨 전 전체 번호를 넘겨보거나 원하는 영수증으로 바로 이동하고, 자동 번호를 다시 뽑을 수 있습니다.
- 결과 맨 위에서 1~5등과 꽝의 전체 게임 수를 한 번에 확인합니다. 가상 구매 비용·당첨금·손익과 긴 운 풀이는 접어서 표시합니다. 반복되는 반응 문구·친구 유형 제안·버튼의 두 번째 캐릭터를 덜어내고 1등 결과와 다음 도전을 강조합니다.
- 등수별 집계는 `3등 0번`, `4등 3번`처럼 단위를 붙입니다. 1등은 `1억원치, 100,000게임을 돌렸지만… 1등은 0번`처럼 실제 완료한 구매 금액과 총 게임 수를 크게 표시하고, 아래에 추첨 횟수와 회차당 게임 수를 따로 설명합니다. 0번일 때는 짙은 남색 카드에 숫자가 찍히고 카드가 짧게 흔들리며 `이번엔 1등 운이 없네요…` 문구와 함께 회색 영수증 조각이 떨어집니다. 1등이 있으면 금빛 카드와 양쪽 축포를 3.2초간 재생합니다. 축포는 최대 160개, 낙첨 종이 조각은 최대 84개의 캔버스 입자만 사용하며 결과당 한 번만 재생하고, 화면 전환·백그라운드·크기 변경 시 즉시 정리합니다. 모션 감소에서는 정적인 강조만 표시합니다.
- 당첨이 있는 영수증 중 최고 등수의 게임을 먼저 표시합니다. 전체·당첨 있음·전부 낙첨 필터, 장 번호 바로 이동, 빠른 탐색 막대, 좌우 버튼·스와이프·방향키를 지원합니다. 영수증 장 번호는 필터와 관계없이 전체 구매 내역의 번호입니다.
- 영수증 한 장의 최대 5게임만 DOM에 표시합니다. 각 영수증은 해당 회차의 당첨번호와 대조하며, 당첨 게임은 초록색 등수 배지, 낙첨 게임은 회색 배지로 구분합니다. 맞힌 번호에는 빨간 동그라미, 보너스에는 파란 점선을 표시합니다.
- 직접 영수증을 넘길 때만 짧은 종이 넘김 애니메이션을 재생합니다. 자동 넘김은 없으며 모션 감소 설정을 따릅니다.
- 추첨 1~100,000회, 매회 1~1,000게임. 한 실험은 최대 1,000,000게임.
- 매번 자동 번호 또는 직접 마킹한 6개 번호를 모든 회차·게임에 고정.
- 중복 없는 당첨번호 6개와 별도 보너스 번호. 실제 로또 등수 규칙.
- Web Worker에서 12ms 단위로 계산하고, 진행률은 최대 10Hz로 갱신합니다. 진행 메시지에는 복권 배열을 보내지 않습니다. 모든 번호·등수·회차별 당첨번호는 바이트 배열에 기록하고, 완료 시 `ArrayBuffer` 소유권을 한 번만 이전합니다. 번호 기록용 버퍼는 최대 설정에서도 7.7MB 이하입니다. 당첨·낙첨 영수증 인덱스는 단일 버퍼를 공유해 메모리를 절반으로 줄였습니다. 10억원 기본 구성에서 전체 기록과 인덱스는 총 7,807,000바이트입니다. 중단 시 미사용 버퍼를 잘라내고, 다음 실험에서 이전 기록을 해제합니다. 진행 중에는 숨겨진 결과 DOM을 다시 만들지 않습니다.
- 가상 비용, 등수별 당첨 수, 예시 당첨금과 가상 손익.
- 추첨 후 결과 전용 화면으로 이동. 최고 등수·당첨 수·손익·마지막 회차의 근접 결과에 따른 24가지 운 유형.
- 자동 구매에서 최고 3등인 결과는 당첨 게임 수 1·2·3·4·5·6회 이상에 따라 여섯 유형으로 나눕니다. 10만 게임을 넘으면 구매 규모에 따른 기대 당첨 수와 편차로 조정해 최대 설정에서도 한 유형으로 몰리지 않습니다. 같은 번호를 여러 장 산 고정 모드는 중복 게임 수로 유형을 높이지 않습니다. 2등 여러 게임, 구매 규모에 비해 4등이 적거나 많은 적자 결과도 별도 유형입니다. 실제 등수와 당첨 집계는 그대로입니다.
- 모든 결과에 **“나는 N%의 행운아 / 현실 로또인 / 꽝손”** 카드를 표시합니다. 이번에 완료한 게임 수와 등수별 당첨 횟수를 설명하고, 드문 당첨·평범한 당첨·전부 낙첨을 구분합니다. `왜 이 확률인가요?` 안에서 계산 기준을 확인할 수 있습니다. 모바일에서는 영수증보다 먼저 보여줍니다.
- 오리지널 로또 공 캐릭터 5종, 24가지 운 유형, 유형별 6가지 한 줄 멘트(총 144개). 기존 유형과 긴 풀이는 확률 설명 안에 접어두어 화면의 중복 문구를 줄였습니다. 같은 시드의 링크는 같은 확률·유형·문구를 재현합니다.
- 왕관 캐릭터와 1등 축하 문구는 현재 당첨 집계에 실제 1등이 있을 때만 표시합니다. 2·3등은 해당 등수에 맞는 캐릭터를 쓰며, 1등이 없어도 충분히 드문 결과이면 그에 맞는 행운 문구를 표시합니다. 공유 이미지에도 같은 기준을 적용합니다.
- 도전장 링크를 열면 친구의 결과를 그대로 재현. 같은 금액·설정, 새 시드로 도전하고 실제 가상 당첨금을 비교합니다.
- 캐릭터·이번 결과의 확률·당첨 근거가 담긴 1080×1440 결과 카드 PNG 저장과 지원되는 기기의 네이티브 공유. 첫 1등 누적 도전 카드에는 누적 금액도 유지합니다.
- 모바일, 키보드, 스크린 리더, 모션 감소 설정 지원.

로그인, 결제, 실제 구매, 번호 예측 기능은 없습니다. 추첨은 브라우저에서 계산합니다.
게임 수에 비례하는 서버 요청이나 저장소 쓰기는 없습니다. 정적 파일은 CDN에서 전달하며,
동시 방문자가 늘어도 시뮬레이션 연산은 각 사용자의 기기에 분산됩니다. 트래픽·호스팅 한도는 별도로 적용됩니다.
공유 링크에는 번호 설정, 재현용 시드와 수동 번호가 들어갑니다. 공개 서버에 방문자별 추첨 기록을 저장하지 않습니다.

## 실행

런타임 의존성과 빌드 과정이 없는 HTML/CSS/JavaScript 사이트입니다.
정적 웹 서버에서 열어주세요. `file://`에서는 모듈과 Worker가 작동하지 않습니다.

```sh
python3 -m http.server 4176 --bind 127.0.0.1
```

[로컬 미리보기](http://127.0.0.1:4176/)

검증은 Node.js 20 이상에서 실행합니다. `npm install`은 필요하지 않습니다.

```sh
npm test
```

## 정적 배포와 전송량

Vercel의 정적 파일 CDN을 사용하며 서버 함수나 DB가 필요하지 않습니다.
`deployment/vercel.json`은 운영 사이트의 `/lotto/assets/`에만 브라우저 캐시 24시간을 지정합니다.
이 사이트가 포함된 상위 배포 디렉터리의 `vercel.json`으로 복사해서 사용합니다.
다른 웹 호스트나 경로로 배포할 때는 해당 호스트의 캐시 설정과 경로에 맞추세요.
HTML과 실행 코드는 배포 후 갱신될 수 있도록 기본 재검증 정책을 유지합니다.
자산을 수정할 때는 참조 URL의 버전도 변경해야 합니다.

화면의 한글 글꼴은 이 프로젝트의 문구에 필요한 글자만 담은 `assets/lotto-sans.woff2`를 사용합니다.
원본 글꼴은 재생성을 위해 남겨두며 페이지에서 다운로드하지 않습니다. 폰트의 내부 이름은
OFL의 Reserved Font Name 조건에 맞춰 Lotto Sans로 변경했습니다. 새로운 문구를 추가하면 다음을 실행하세요.

```sh
uv run --with 'fonttools[woff]' python scripts/subset-font.py
```

생성 스크립트가 현재 HTML/JS/CSS에서 사용하는 글자를 수집하고, 지원하던 글자가 빠지지 않았는지 검사합니다.
위 도구는 글꼴 생성에만 필요하며, 배포된 사이트와 일반 실행·테스트에는 의존성이 없습니다.
이 구조는 추첨 횟수에 따른 서버 부하를 없애지만, 실제 대규모 부하 시험을 뜻하지는 않습니다.
CDN 전송량·요청 수와 호스팅 요금제 한도는 방문자 수에 따라 적용됩니다.

## 확률과 당첨금

1등 확률은 정확히 `1 / C(45, 6) = 1 / 8,145,060`입니다.
자동 모드는 각 게임의 번호를 독립적으로 고르므로 중복 조합이 나올 수 있습니다.
N게임 중 1등이 한 번 이상 나올 확률은 `1 - (1 - 1/8,145,060)^N`입니다.
계산은 작은 확률에서도 정밀도를 유지하는 `log1p`와 `expm1`을 사용합니다.

고정 모드는 매회 모든 게임이 같은 번호입니다. 한 회차에 같은 번호를 여러 장
사도 1등을 만날 확률은 늘지 않으므로 누적 확률의 N은 추첨 횟수입니다.
당첨 시 해당 회차의 동일 번호 게임은 모두 같은 등수로 집계합니다.

| 등수 | 조건 | 이 실험의 세전 금액 |
| --- | --- | --- |
| 1등 | 6개 일치 | **예시** 20억 원 |
| 2등 | 5개 + 보너스 일치 | **예시** 5,000만 원 |
| 3등 | 5개 일치, 보너스 불일치 | **예시** 150만 원 |
| 4등 | 4개 일치 | 고정 5만 원 |
| 5등 | 3개 일치 | 고정 5천 원 |

실제 1~3등 금액은 판매액과 당첨자 수에 따라 변합니다. 이 시뮬레이터는 세금,
판매액, 당첨자 간 배분과 이월을 구현하지 않습니다. 가상 회수율은 이번 결과의
예시 당첨금 / 가상 구매 비용이며 실제 복권의 기대 회수율이 아닙니다.
이전 결과는 다음 회차의 당첨 확률을 바꾸지 않습니다.

## 내 결과의 행운 확률

표시하는 값은 실제 이용자 중 상위 비율이 아니라 **같은 조건에서 이 정도 이상 당첨될 이론 확률**입니다.
최고 등수를 `r`, 그 등수의 당첨 횟수를 `k`라 하면, 더 높은 등수가 한 번이라도 나오거나
최고 등수 `r`이 `k`번 이상 나오는 경우를 셉니다. 하위 등수별 당첨 횟수는 설명에 표시하지만
그 확률을 각각 곱하지 않습니다. 특정 당첨 내역의 희소성을 행운인 것처럼 과장하지 않기 위해서입니다.

한 게임의 전체 조합 수는 `C = 8,145,060`이고 1~5등 조합 수는 각각 `1, 6, 228, 11,115, 182,780`입니다.
더 높은 등수들의 확률 합을 `a`, 해당 등수의 확률을 `b`, 독립 시행 수를 `N`이라 하면:

```text
P = 1 - (1-a)^N + (1-a)^N × P(Binomial(N, b/(1-a)) >= k)
```

자동 모드는 완료한 게임 수를 사용합니다. 고정 모드는 같은 회차의 모든 게임이 함께 당첨되므로
완료한 추첨 횟수와 해당 등수에 당첨된 회차 수를 사용합니다. 전부 낙첨한 경우는
`(7,950,930 / 8,145,060)^N`을 표시하고 행운아 대신 꽝손 문구를 씁니다.
이번 실험만 계산하며 10억원 누적 도전의 이전 실험 금액은 확률에 포함하지 않습니다.
예를 들어 자동 100만 게임에서 1등 2번이면 1등이 2번 이상 나올 확률은 약 **0.695%**입니다.

`luck.js`는 작은 확률에 안정적인 로그 계산과 이항분포 꼬리 합을 사용합니다.
독립적으로 생성한 [SciPy 이항분포 계산](https://docs.scipy.org/doc/scipy/reference/generated/scipy.special.bdtrc.html)
결과와 대조하며, 극히 작은 값은 0% 대신 `<0.000001%`로 표시합니다.
브라우저에서 결과마다 한 번 계산하고 재사용하므로 별도 서버 요청이나 의존성이 없습니다.
이 별명은 미래의 당첨 가능성이나 개인의 고정된 운을 뜻하지 않습니다.

## 추첨 구현

`core.js`는 DOM과 분리된 추첨 모델입니다. `worker.js`가 짧은 시간 단위로
실행·중단하며 `app.js`는 구매 영수증, 결과 화면과 공유를 담당합니다.
`profiles.js`는 실제 실험 결과를 바탕으로 재미있는 별명과 풀이를 고릅니다.
`luck.js`는 당첨 등수·횟수·독립 시행 수로 결과의 이론 확률과 설명을 만듭니다.
`draw-reveal.js`는 계산과 독립된 추첨 공개 순서와 대기 시간을 담당합니다.
`first-prize.js`는 전체 게임 수에 맞춘 1등 문구와 짧은 결과 연출을 담당합니다.
`journey.js`는 10억원 누적 도전과 재열람 중복 방지를 담당하며 영수증을 보관하지 않습니다.
번호 공개가 끝나도 Worker 계산이 완료될 때까지 기다리며, 취소한 연출의 타이머는 정리됩니다.
심리검사나 실제 운의 측정이 아닙니다. 시드에 따라 한 줄 멘트도 재현됩니다.

번호 미리보기는 동일 시드의 첫 회차에서 구매 번호만 가져옵니다.
실제로 시작할 때 그 시드를 사용하므로 구매 번호가 추첨 도중 바뀌지 않습니다.
`receipts.js`는 모든 완료 회차의 구매 내역을 압축 없이 바이트 단위로 저장하고,
당첨이 있는 영수증과 전부 낙첨인 영수증의 장 번호를 Worker에서 인덱싱합니다.
한 회차의 구매 번호를 최대 5게임씩 나누므로 서로 다른 회차가 한 영수증에 섞이지 않습니다.
전체 기록을 보관하되 화면에는 선택한 한 장만 만듭니다. 100회 추첨도 첫 회차부터 마지막까지 조회할 수 있습니다.
새 공유 링크의 `#result`는 결과 화면을 바로 열고, `c=1`은 친구 도전장을 표시합니다. 기존 버전 1 링크도 지원합니다.
친구와의 비교는 도전하는 브라우저 세션 안에서만 유지되며, 내 결과를 다시 공유하면 내 결과가 새 도전장의 기준이 됩니다.

초기 128비트 시드는 `crypto.getRandomValues`로 만듭니다. 재현 가능한
xoshiro128** PRNG, 모듈로 편향을 제거하는 rejection sampling, 부분 Fisher–Yates
셔플을 사용합니다. PRNG는 시뮬레이션용이며 실제 복권 번호 예측용이 아닙니다.
공유 버전 1의 PRNG, 샘플 순서 또는 등수 규칙을 바꾸면 `VERSION`을 올려야 합니다.

영수증 탐색은 [W3C의 사용자 제어·키보드 탐색 가이드](https://www.w3.org/WAI/tutorials/carousels/)를 참고했습니다.
버퍼 이전은 [MDN의 transferable objects 문서](https://developer.mozilla.org/en-US/docs/Web/API/Web_Workers_API/Transferable_objects)를 참고했습니다.
